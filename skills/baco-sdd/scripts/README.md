# BACO-SDD verification engine

Zero-dependency Node CLI (Node >= 22, ES modules) that mechanically verifies a specification against code, tests and git history. It is the contract between the BACO-SDD skill (AI agents) and the repository: agents call it and read its exit codes and `--json` output; they do not re-implement these checks.

```
node skills/baco-sdd/scripts/baco.mjs <command> [args] [--json] [--cwd <dir>]
```

This README documents what the code does. Where the code and any plan disagree, the code wins.

## Conventions

- Every command accepts `--json` (prints the command's `data` object as JSON on stdout, instead of the human messages) and `--cwd <dir>` (default: current directory). With `--json`, an exit code of 64 or more is never silent: the localized messages still go to stderr, and the JSON gets an extra `error: {key, params}` (the first message; for an error raised outside the command, e.g. delivery not found, the JSON is just `{ "error": {...} }`). Successful output keeps the command's `data` shape. The repo root is `git rev-parse --show-toplevel` of `--cwd`, so commands work from subdirectories. Outside a git repo every command except `validate-spec` and `queue-status` exits 65.
- Human text comes from `lib/messages.mjs`, in pt-BR (default) or en, selected by `language` in `.baco/config.yaml`. `--help` is always pt-BR. Human messages go to stdout when the exit code is 0-2 and to stderr for 3 and above.
- Flags are `--name value` or `--name=value`; a flag repeated becomes a list (`--junit a.xml --junit b.xml`). A flag followed by another `--flag` or nothing is boolean `true`.
- Unexpected exceptions exit 1 (`BACO_DEBUG=1` prints the stack). Missing files (ENOENT) exit 65; git errors (e.g. a bad ref) exit 65; config parse errors exit 65; a delivery `ENT-NNN` that is not found or ambiguous exits 65 (`delivery.not_found` / `delivery.ambiguous`, mapped once in the dispatcher).
- The `git` binary: when running it fails the way the macOS `xcrun` shim does inside a sandbox (exit 72, or stderr containing `xcrun: error`) or the binary is not found, the engine retries with the first existing of `$BACO_GIT`, `/Library/Developer/CommandLineTools/usr/bin/git` and `/Applications/Xcode.app/Contents/Developer/usr/bin/git`, and remembers the one that worked for the rest of the process. `BACO_GIT` (a path to a git executable) is also tried first when set. If none works, the command exits 65 with `env.git_unavailable` ("version control did not respond"), distinct from `env.not_git_repo`; this applies to every command that needs a repo, including `plan-freshness` and `guard-tests`.
- Config: `.baco/config.yaml` (minimal YAML subset: maps, `- ` lists, inline `[a, b]` / `{k: v}`, scalars, `#` comments, no tabs), deep-merged over defaults. Keys used by the engine: `language`, `docs_root` (default `docs`), `branches.main` (default `main`), `branches.integration` (default `develop`), `branches.protected` (default `main, master, develop`), `tests.patterns` (globs of test files; `*`, `**`, `?` and `{a,b}` alternation; default `**/*.test.{js,jsx,ts,tsx,mjs,cjs}`, `**/*.spec.{js,jsx,ts,tsx,mjs,cjs}`, `**/e2e/**/*.{js,jsx,ts,tsx,mjs,cjs}`, `.maestro/**/*.{yaml,yml}`), `tests.junit_dir` (default `.baco/junit`), `tests.<layer>` (the command of a test layer: every other key of `tests` except `junit_dir`, `patterns` and `queue`), `tests.queue` (layers whose runs are serialized machine-wide by `run-tests`; default: every layer whose name starts with `e2e`; `[]` disables the queue), `tests_quick.<layer>` (optional quick command of a layer for `run-tests --quick`, e.g. one browser only; a layer without one falls back to `tests.<layer>`), `app.smoke` (optional non-interactive command that starts the app the way the user does, checks it answers and exits; 0 = ok), `manual_pending` (default `{main: block, '*': warn}`), `review.external_rounds_max` (default 3), `review.pr.reviewer` (default `agente`: who reviews the delivery's pull request, `agente`, `pessoa` or `ambos`) and `review.pr.auto_fix` (default `true`: whether the reviewer's findings become fix tasks that run on their own; a boolean); a bad `auto_fix` is dropped (the default stays) with `config.invalid_section` naming `review.pr.auto_fix`; a bad `reviewer`, or a `review.pr` that is not a map, becomes `reviewer: pessoa` (the most human review, never a silent agent review) with the warning `config.pr_reviewer_invalid`; no engine command reads them, the conductor does. `harnesses` (default `{}`: the AI tools the project uses, by name, for example `claude-code`, `codex`, `opencode`; each a map with `models`, from the levels `forte`, `medio`, `leve` to that tool's model names, and `implementers`, default `false`, whether the tool may run implementers when it is not the conductor's own tool); an entry that is not a map, a level other than those three, an empty model name or an `implementers` that is not a boolean is dropped with `config.invalid_section` naming `harnesses.<name>[.<key>]`; no engine command reads it, the plan does. `provenance.ignore` (default `[]`: repo-relative path globs, git pathspec `glob` style, e.g. `docs/registro-da-rodada.md`, `logs/**`; a commit that touches only these paths, like one under `<docs_root>/entregas/**`, does not make a recorded head stale, see R26 in `acceptance-report`; a leading `./` is removed; an item is dropped with the warning `config.invalid_section` naming `provenance.ignore`, and so is a value that is neither a list nor a scalar, when it is not text, is empty, absolute or starts with `:`, or when it could hide what the freshness check exists to see: (1) made only of wildcards, dots and slashes (`*`, `**`, `**/*`, `?`, `.`, `./`, `/`), which would hide every change; (2) with a `.` or `..` segment (`../x` points outside the repo, which git refuses); (3) with `[`, `]` or `\`, which the check below does not understand; (4) covering the engine's files: an entry that matches `.baco/config.yaml`, `.baco/local.env` or `.baco/junit/*.xml`, or whose first segment (unless it is `**`) matches `.baco`, so a config change can never hide itself; (5) covering test files, judged against the default `tests.patterns` plus the project's own: refused when the entry matches an example path of a test pattern (each `**` there taken as no folder, one folder, or the folders the entry names before the pattern's own folder, so `src/e2e/**` meets `**/e2e/**`) or when a test pattern matches an example path of the entry (so `src/a.test.js`, `**/*.spec.ts`, `**/*.js`, `e2e/**`, `.maestro/**` are refused); a pattern that names only file names, like `**/*.test.js`, is not applied to a folder glob, so `logs/**` stays. Explicit files and folder globs such as `docs/registro-da-rodada.md`, `docs/registros/**`, `logs/**` or `**/*.log` are kept. The check cannot tell a code folder from a log folder (`src/**` is kept like `logs/**`); that is what the `guard-tests` finding `CONFIG_PROVENANCE_CHANGED` and the intersection rule of R26 are for), `models.<class>` (classes `mechanical`, `standard`, `risky`; each `{ level: forte|medio|leve, effort: alto|medio|baixo }`, defaults `leve/baixo`, `medio/medio`, `forte/medio`). Levels never name a model: `forte` is the most capable model of the environment, `medio` the intermediate one, `leve` the fastest and cheapest. The old form `{ model: opus|sonnet|haiku, effort: high|medium|low }` still loads (opus=forte, sonnet=medio, haiku=leve; high, xhigh and max=alto, medium=medio, low=baixo); `level` wins over `model` when both are given. An unrecognized value is ignored (the default for that field stays) with the warning `config.invalid_section` naming `models.<class>.<field>`. `baco cost add --model` is unrelated: it records the real model name as a free string. `context.handoff_at` (default 290000: conversation size, in tokens of context, from which the plugin hook `hooks/context-size.mjs` warns the conductor to continue in a new conversation; a positive integer) and `context.auto_handoff` (default `false`: whether, during phases 6 and 7, the conductor may switch conversations without asking; a boolean, `on`/`off` or `true`/`false`); a value of the wrong type is dropped (the default stays) with `config.invalid_section` naming `context.<key>`. `github.project` (unset by default; `owner` non-empty, `number` a positive integer, optional `field`, default `Status`, and `status` with keys `published`, `started`, `review`, `merged`, defaults `Backlog`, `In progress`, `In review`, `Done`): the board `baco board` mirrors, used only with `github` in `tracker`; a project without a valid owner and number is dropped with `config.invalid_section` naming `github.project`, and a bad field or status entry keeps its default with the warning naming it. No engine command reads `context`; the hook does. The hook's effective limit is the smaller of `context.handoff_at` and the point where Claude Code summarizes the conversation by itself, about its `autoCompactWindow` setting minus 33000 tokens (measured: 18 automatic summaries between 366000 and 375000 tokens with a 400000 window; never below half the window), read from `.claude/settings.local.json`, `.claude/settings.json` and `~/.claude/settings.json` in that order, failing open, minus a safety margin of 30000 tokens (at most half of that point), because a step adds 10000 to 20000 tokens; with a 400000 window the limit is 337000, so the default `handoff_at` of 290000 comes first. The warning names the effective limit and the auto-compact point. Version change: the `SessionStart` hook `hooks/baco-context.mjs` records, per session (not after a summary, `source: compact`, which keeps the record), the version of the running plugin (`CLAUDE_PLUGIN_ROOT` in Claude Code, else the hooks' parent folder; `.claude-plugin/plugin.json`, then `plugin.json`, then the skill's `metadata.version`); `context-size.mjs` then says once per newer version, main conversation only, when the plugin cache holds a newer version folder beside the running one (`.../<plugin>/<X.Y.Z>/`; a folder whose name is not a version, such as a checkout, has no siblings to compare), telling the conductor to save `## Retomada` and give the person the title and the request for a new conversation, without opening it. Harness files: `hooks/baco-context.mjs` also adds, for the conductor only, a note naming each file `scripts/lib/harnessfiles.mjs` finds missing or different from the skill template (`harnessFileChecks(root, config)` returns `{file, template, harnesses, status: ok|missing|different}` per required file: a harness whose name or `tool` contains `codex` needs `.codex/rules/baco.rules` equal to `templates/codex/baco.rules`, one containing `antigravity` needs `.baco/antigravity/leitura.json` equal to `templates/antigravity/leitura.json`, case-insensitive), so the conductor offers to copy them now. The same hook (`PostToolUse`, main conversation only) reminds the conductor to update `## Retomada` when a task branch `baco/ENT-NNN-T-NNN` is not merged into its delivery branch and the delivery's `progresso.md` was last modified more than 30 minutes ago: at most one reminder per 30 minutes per session, and the check itself runs at most every 5 minutes (state files under the per-user folder in `os.tmpdir()`). The pure decisions are in `scripts/lib/hookrules.mjs`.
  - Gates `spec_approval`, `irreversible_action` and `merge_main` are ALWAYS `true` in the resolved config. Any user value for them other than boolean `true` (`off`, `"off"`, `0`, `no`, ...) is ignored with the warning `config.mandatory_gate_ignored` on stderr.
  - `gates`, `branches`, `tests`, `models`, `review`, `manual_pending`, `tests_quick`, `app`, `provenance`, `context`, `harnesses`, `github`, `planning`, `roles`, `test_runs`, `ci`, `delivery` and `qa` must be maps. Any other non-empty value (e.g. `gates: off`) is ignored, the defaults are kept, and the warning `config.invalid_section {section}` is printed. An empty value also keeps the defaults, silently.
  - A single scalar in `branches.protected`, `tests.patterns`, `tests.queue` or `provenance.ignore` (and a single text in `review.focus.always`, `review.focus.suggestion` or `qa.specialist`) is read as a one-element list.
  - Keys added in 1.10.0, all optional, read by the conductor and the planner (in the engine, only `baco merge-check` reads `delivery.integration_merge` and `test_runs.ci_full`); a bad value is dropped (the default stays) with `config.invalid_section` naming `<section>.<key>`:
    - `planning.risk` (default `{}`): the project's own criterion per risk class, free text with examples, keys `arriscada` and `mecanica` (`mecânica` and any case are folded); `padrao` is everything else and a missing class uses the generic criterion. Another key, an empty or non-text value, or a `risk` that is not a map is dropped (warning `planning.risk.<key>` or `planning.risk`).
    - `planning.max_tasks` (default 8) and `planning.max_criteria` (default 60): integers >= 1; above them the planner proposes splitting the delivery. `planning.freeze_specs` (default `true`, a boolean): after the plan is approved, a spec change goes to the next delivery unless the person decides to bring it in.
    - `review.focus` (default `{ always: [], suggestion: [] }`): lists of non-empty texts; a finding of a `suggestion` class is a `sugestão` unless it touches an `always` item. Bad items are dropped with one warning naming the list; a list that is neither a list nor a text, another key, or a `focus` that is not a map is dropped. `review.final_rounds_max` (default 2, integer >= 1): the internal final review runs whole once, then at most N-1 delta rounds.
    - `test_runs.screen_task_full` (default `false`, a boolean) and `test_runs.ci_full` (`merge`, default, or `manual`).
    - `ci.monthly_minutes` (default `null`: unknown; integer >= 1): the CI plan's monthly minutes, for the plan's CI estimate.
    - `delivery.target` (`integration`, default, or `main`) and `delivery.integration_merge` (`ask`, default, or `auto`).
    - `qa.specialist` (default `[]`, a list of non-empty texts): kinds of manual scenario only a specialist QA runs (marked `manual, especialista: <tipo>` in the QA file, see File formats).
  - `manual_pending` keys `main` and `integration` are ROLE names: they apply to the branch named in `branches.main` / `branches.integration` (with `branches: {main: master}`, the `main` rule applies to target `master`). Any other key is a literal branch name and wins over a role. `'*'` is the fallback; with nothing matching, the rule is `warn`.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | ok |
| 1 | verification failed (or unexpected error; `run-tests`: a test layer or the smoke check failed) |
| 2 | human gate required |
| 3 | human decision required (review loop limit) |
| 64 | usage error (missing/invalid arguments; also `build-handoff` with no base ref or a refused `--dest`; `run-tests` with an unknown layer, a layer without command or no `app.smoke`) |
| 65 | environment error (not a git repo, git did not respond, missing file, delivery not found or ambiguous, bad ref, bad config, malformed or `--ca`-filtered trace JSON in `acceptance-report` or `build-handoff`, a `provenance.ignore` entry git refuses in `acceptance-report`, `spec-diff` file outside the repo, `run-tests` queue wait timed out or the shell could not be started) |

## Commands

### validate-spec
`baco validate-spec <spec.md>` — lints a spec file. Works outside a git repo. Exit 0 (no error-level findings; warnings allowed), 1 (at least one error), 64. `data`: `{ path, code, version, counts: {RF,RN,RNF,INV,CA}, retired: [ids], nextFree: {line, declared, minimum}, findings: [{level, code, line, id?, ...}] }` (`retired`: IDs the spec records as retired, see Spec; `nextFree`: see Spec, Next free numbers; the `NEXT_FREE_*` findings add `series`, `max`, `declared`, `minimum` or `value`).
Findings: errors `DUPLICATE_ID`, `CA_MISSING_GWT` (a CA lacking Dado/Dada/Dados/Dadas, Quando or Então as whole words, in its text or table headers), `MISSING_ACCEPTANCE_SECTION` (no heading containing "aceite"), `VERSION_MISMATCH` (metadata version differs from last history row), `RETIRED_ID_REDEFINED` (an ID the spec records as retired is defined again), `NO_DEFINITIONS` (no definition recognized, but the text cites an RF/RN/RNF/INV/CA ID of the spec's code that is not retired; `line` is the first such line); warnings `MIXED_CAPABILITY_CODE`, `DANGLING_REF` (references to retired IDs are not dangling), `NO_HISTORY`, `NEXT_FREE_STALE`, `NEXT_FREE_MISSING_SERIES`, `NEXT_FREE_INVALID` (see Spec, Next free numbers), `UNRECOGNIZED_DEFINITION` (a line that leads with an RF/RN/RNF/INV/CA ID like a definition but in a shape the engine does not read: a paragraph such as `**RF-XYZ-024 | Title.** text`, a numbered or `+` list item, a bullet with a dash after the ID, a heading with no separator after the ID, or a row of a definition table whose first cell holds an ID the engine cannot read).

### spec-diff
`baco spec-diff <spec.md> --base <ref|auto>` — compares definitions (by ID and normalized text) between the spec at a git ref and the working-tree file. Exit 0, 64, 65 (bad ref, file outside repo). `--base auto` uses the sha in the catalog's `Versão implementada` for the spec's code; with none recorded, everything is reported as added. A spec that does not exist at the ref also yields everything added. `data`: `{ path, base: {ref, sha, version}, head: {version}, added[], modified[], removed[], reclassified[] }` (IDs sorted RF, RNF, RN, INV, CA). `reclassified`: an ID that is a definition on one side only, while the other side still has a row, bullet or heading leading with it with the same normalized text (e.g. a renamed heading turned a table into a matrix); it only changed how the engine reads it, so it is listed here and never in `added` or `removed`. A retired ID is not a definition on either side, so renaming a retired-ID table changes nothing.

### catalog
`baco catalog get <CODE>` / `baco catalog set <CODE> [--implemented <version>@<sha>@<ENT-NNN>] [--impl-state <s>] [--validation <s>] [--validated <version>]` — reads or edits one row of `<docs_root>/catalogo-de-specs.md`. `set` rewrites only the touched row (adds the two version columns on first use) and keeps all other bytes. Exit 0, 64 (bad flag value, unknown state, sha not 7-40 hex, unknown code or column), 65 (catalog missing). `--impl-state` allowed: `não iniciada`, `em implementação`, `implementada`, `não verificada`. `--validation` allowed: `pendente`, `parcialmente validada`, `validada`, `validada sem revisão externa`, `não conforme` (exact text, accents and spaces as written). Use `validada sem revisão externa` when every criterion of the spec is proven and the external review was waived with `waive-review` (so there is no approved verdict); `validada` needs the approved verdict. `data`: the row as `{header: value}`.

### trace
`baco trace --spec <spec.md> --qa <qa.md> [--junit <file.xml>]... [--delivery ENT-NNN] [--ca <CA-ID>[,<CA-ID>...]]... [--out <file.json>]` — builds CA -> QA scenario -> test coverage. JUnit files default to every `*.xml` in `tests.junit_dir`. The JSON records provenance: the HEAD sha, the spec path (relative to the repo root) and version, and the delivery. With `--delivery ENT-NNN`, only evidence rows of that delivery count; rows of other deliveries are ignored (the scenario becomes `manual_pending`). With `--delivery`, the IDs of every spec in the delivery's plan header (`**Specs:**`: each spec's definitions and the scenarios of its QA file at `<spec dir>/../qa/cenarios-qa-spec-<name>.md`, when it exists) are also known, so a test tagged with an ID of another spec of the same delivery is not listed in `orphanTests`; only IDs unknown to all of them are. A delivery with no folder or no plan adds nothing (the rule is then the one without `--delivery`). `--ca` (repeatable, or a comma list) restricts `cas`, `summary` and the exit code to those criteria, in spec order; it is meant for the end of each task, to catch a missing criterion tag at once. The JSON then records `filter: [ids]` (`null` without `--ca`), and such a trace is refused by `acceptance-report` and `build-handoff` (exit 65, `acceptance.bad_trace` / `handoff.bad_trace` with reason `filtered`). QA scenarios whose `Contratos` name no CA of the spec (only a rule, a requirement, or nothing) go to `otherScenarios`, each with `contracts`, `automation`, `tests`, `result` and `evidence` computed exactly like a scenario of a CA (manual without evidence -> `manual_pending`, automated without a JUnit match -> `not_run`), and the text output lists them on one line (`trace.others`); with `--ca` the list is empty. Every QA scenario in the trace carries `tests`: all the test paths of its `Automação` line. Exit 0, or 1 when any (selected) CA is `uncovered` or `failed`, or (without `--ca`) a scenario of `otherScenarios` is `failed`, `manual_fail` or `layer_mismatch`; 64 for missing flags, a malformed `--delivery`, an empty `--ca` item, or a `--ca` id that is not a CA of the spec (`trace.unknown_ca`). `data` is the trace JSON (see below).

### plan-freshness
`baco plan-freshness <ENT-NNN | path/to/plano.md>` — compares each `path@version` in the plan header with the spec's current version (numeric compare; a missing file or unparsable version counts as stale; a missing version is shown as `-`). A plan whose `**Specs:**` lists nothing exits 1 with `freshness.no_specs` (`data`: `{ stale: [], noSpecs: true }`). Exit 0 (fresh), 1 (stale or no specs), 64, 65. `data`: `{ stale: [{path, planned, current}] }`.

### check-branch
`baco check-branch` — fails when the current branch is in `branches.protected`, or is `branches.main` or `branches.integration` (always protected). Exit 0 or 1. `data`: `{ branch, protected }`.

### guard-tests
`baco guard-tests --base <ref> [--head HEAD] [--task-base <ref>] [--allow <ID>]... [--allow-from-spec <spec.md>@<ref>]...` — scans the `base..head` diff of test files and, when the task's start is known, also the `<task start>..head` diff, so a test added by an earlier task of the same delivery (absent at `--base`) is protected in later tasks. The task start is `git merge-base <head> <ref>` for `--task-base <ref>`; without the flag, when the head branch (`--head`, or the current branch for `HEAD`) is a task branch `baco/ENT-NNN-<TASK-ID>` and the local branch `baco/ENT-NNN` exists, it is the merge-base with that branch; otherwise only `--base` counts. When the task start equals `--base`, one scan runs. A finding seen in both scans is reported once (same code, path and ID; for `SKIP_ADDED`, same path and head line); the base scan's findings come first. Each scan reads the test files (globs in `tests.patterns`) for (a) `SKIP_ADDED` (`.skip/.only/.todo/.fixme`, `xit`, `xtest`, `xdescribe`, `fit`, `fdescribe`), (b) `TAGGED_TEST_CHANGED` (a line inside a test whose title carries a `[CT-…]`/`[CA-…]` ID was added or removed), (c) `TAGGED_TEST_DELETED` (a test file with tagged tests was deleted, replaced by another file type such as a symlink, renamed/moved from a test path to a non-test path, or renamed from a test path so that its last extension changes, e.g. `a.test.js` -> `a.test.js.disabled`, whatever the patterns say — the renamed file's hunks are still scanned for `SKIP_ADDED`; a non-test file renamed into a test path is scanned as a normal modification; the IDs are read from the base content, so a 100% rename is caught), (d) `CONFIG_TESTS_CHANGED` (`.baco/config.yaml` changed between base and head and its resolved `tests` section, `tests_quick` section or `app.smoke` differs; `--allow` does not clear it), (e) `CONFIG_PROVENANCE_CHANGED` (`.baco/config.yaml` changed between base and head and its resolved `provenance.ignore` differs, compared as a set after the refused entries are dropped, so reordering or adding a refused entry is not a change; the list decides which files do not count as code for R26, so a change to it needs a person's ok exactly like `CONFIG_TESTS_CHANGED`: `--allow` does not clear it and the exit stays 2). A file is scanned when its old OR new path matches the test patterns. The patterns are the union of `tests.patterns` in the config at `--base` and at the task start (defaults when absent) and in the current config, so a change cannot hide its own test edits by narrowing the patterns. `--allow` whitelists IDs; `--allow-from-spec` whitelists CA IDs modified/removed in that spec since the ref, plus QA scenarios that reference them (QA file is found at `<spec dir>/../qa/cenarios-qa-spec-<name>.md`); it may be repeated, one per spec, and the allowed IDs are the union of all of them (one malformed value exits 64). Exit 0 (clean), 2 (findings: human gate), 64 (missing `--base`, malformed `--allow-from-spec`, `--task-base` without a value), 65 (also a malformed config at `--base` or at the task start, or a bad `--task-base` ref). `data`: `{ findings: [{code, path, id?, line}], taskBase }` (`taskBase`: the task start sha, or null) (`line` is null for `CONFIG_TESTS_CHANGED` and `CONFIG_PROVENANCE_CHANGED`).

### cleanup-branches
`baco cleanup-branches [--apply] [--remote] [--remote-name <name>]` — lists (default, dry run) or deletes merged `baco/ENT-NNN-<task>` branches (merged into `baco/ENT-NNN`, else into the integration branch) and merged `baco/ENT-NNN` branches (into the integration branch). Also deletes the promotion branch `baco/ENT-NNN-PROMO` and `docs/*` branches once merged into the integration branch or into `branches.main` (reasons `promo_merged`, `docs_merged`); one whose tip equals the tip of the target is kept, because an empty new branch cannot be told from one merged by fast-forward. Never touches protected branches or the current branch; skips a branch checked out in the main worktree. `--apply` re-verifies each branch (tip unchanged, still merged) before removing its worktree, tagging deliveries as `entrega/ENT-NNN`, deleting the branch with compare-and-delete. The delivery tag goes on the merge commit that brought `baco/ENT-NNN` into the integration branch: walking the integration branch's first-parent history from the oldest commit not in the delivery tip, the first commit whose second parent is the tip or has it as an ancestor (so a later merge of a release branch that contains the delivery counts too). With no such commit (fast-forward, or merged some other way) the tag falls back to the tip with the warning `cleanup.tag_at_tip`. An existing tag at another commit is never moved (`cleanup.tag_elsewhere`). A created tag is reported in `done[].tag` and `done[].tag_commit`; `--remote` also deletes it on the remote (default `origin`). Remote rule: the remote branch is deleted only when its sha (from `git ls-remote`) equals the verified local sha, and the push uses a lease (`git push --force-with-lease=refs/heads/<b>:<sha> <remote> :refs/heads/<b>`). If the remote branch differs (e.g. another clone pushed commits), it is kept and recorded in `failed` with step `remote_ahead` (`remote_sha`, `local_deleted: true`; the merged local branch is already deleted). In the dry run, `--remote` adds `remote_action` to each candidate (`delete`, `keep_ahead`, `none` or `error`) and prints it. Reasons are shown localized. Exit 0, or 1 when any apply step failed. `data`: `{ apply, candidates, skipped, done?, failed?, warnings? }`.

### build-handoff
`baco build-handoff <ENT-NNN> [--mode pacote|repositorio|pr] [--dest <dir>] [--pr <url|number>] [--qa <path>]... [--trace <file.json>]... [--junit <file.xml>]... [--adr <path>]...` — prepares round NN of the external review and writes `<delivery>/revisao/handoff-NN.md`. Every handoff records its HEAD on the first line (`<!-- baco:head <sha> -->`), in both modes. The delta base is the head of the handoff that the LATEST imported verdict answered (its `reviewedHead`); then the round is a delta (`reviewedHead..HEAD`). With no imported verdict (or one that answered no handoff), the round is full: `plan Base..HEAD`. Two handoffs with no verdict in between are therefore both full. The diff is two-dot (`base..head`).
- The diff ALWAYS excludes `<docs_root>/entregas/**` (progress log, implementer reports, earlier packets and verdicts), in full and delta rounds alike: pathspec `. ':(exclude)<docs_root>/entregas/**'`.
- In a delta round, a plan spec whose file did not change between the reviewed head and HEAD (`git diff --quiet <reviewedHead> HEAD -- <spec>`) is not repeated: its heading is followed by one localized line, `Sem mudanças desde a rodada N.` / `Unchanged since round N.`, where N is the number of the handoff that verdict answered. Same for each `--adr` file (an ADR outside the repository is always included). A spec or ADR that changed is included in full. Full rounds include everything.
- `--mode pacote` (default): `handoff-NN.md` is the self-contained packet: how-to note for the human, reviewer prompt ([`templates/pt-BR/prompt-revisor.md`](../templates/pt-BR/prompt-revisor.md)), spec definitions (RF/RN/RNF/INV/CA) of the plan's specs, ADRs, test status and failing tests, and the filtered diff. `--dest` is a usage error in this mode.
- `--mode repositorio [--dest <dir>]`: exports the tree at HEAD, without `<docs_root>/entregas/**`, to a folder outside the repository (`git archive HEAD -- <pathspec>` extracted with `tar -x`; committed files only, no `.git`, untracked files absent). Default dest: the sibling folder `<repo-folder-name>-revisao-ENT-NNN-rNN` (NN = this round). A dest inside the repository (symlinks resolved) or an existing dest that is not an empty folder is refused with exit 64 (`handoff.dest_inside_repo`, `handoff.dest_not_empty`) before anything is written. Into the copy it writes `REVISAO.md` (the reviewer prompt for this mode, [`templates/pt-BR/prompt-revisor-repositorio.md`](../templates/pt-BR/prompt-revisor-repositorio.md); the delivery, round, base and head shas; the spec and ADR paths to read, each marked changed or unchanged since round N in a delta; test status from `--trace`/`--junit`) and `mudancas.diff` (the same filtered diff). The `handoff-NN.md` in the repository then holds only the mode, the export path and a short prompt for the reviewer, not the diff. The engine never deletes an exported folder.
- `--mode pr [--pr <url|number>] [--qa <path>]...`: the review of the delivery's pull request, in place (the reviewer reads the project at its root, read-only). It writes, in the git-ignored folder `.baco/logs/revisao-pr/ENT-NNN-rNN/` (NN = this round): `mudancas.diff` (the same filtered diff, so the reviewer never needs `<docs_root>/entregas/**`) and `pedido.md` (the reviewer prompt for this mode, [`templates/pt-BR/prompt-revisor-pr.md`](../templates/pt-BR/prompt-revisor-pr.md), which forbids opening `<docs_root>/entregas/`, `.baco/logs/` other than its own request, diff and answer, earlier rounds, `gh` and git history of other commits or branches; the delivery and round; base and head shas; the path of `mudancas.diff` and of the answer file `resposta.md`, the only file the reviewer may create; the spec paths with versions, the `--qa` paths and the `--adr` paths, each marked changed or unchanged since round N in a delta; test status from `--trace`/`--junit`). Every path in `pedido.md` is relative to the repo root. The request never carries the PR given with `--pr`: `gh pr diff` or `gh pr view` would show the delivery folder. This is an instruction to the reviewer, not an enforced isolation (it reads the project in place); `--mode repositorio` is the one that enforces it. It never writes `resposta.md`: that is the reviewer's answer, written by the harness that ran it (for example `codex exec -o`), and imported by `import-pr-verdict`. The `handoff-NN.md` in the repository holds only the mode, the PR (or, without `--pr`, a line saying the review runs on the local diff of the delivery branch), the request and answer paths relative to the repo root and how to use them. The round number follows `handoff-NN.md`, so an existing round folder means an earlier run stopped before writing its handoff: the folder is reused and `pedido.md` and `mudancas.diff` are rewritten (an old `resposta.md` left there is then older than `pedido.md`, and `import-pr-verdict` refuses it); a round path that exists and is not a folder is refused with exit 64 (`handoff.dest_not_empty`). If `git check-ignore` says `.baco/logs/` is not ignored, the warning `handoff.pr.logs_not_ignored` suggests adding it to `.gitignore`. `--pr` and `--qa` are usage errors in the other modes, `--dest` in this one.
- Every prompt lets the reviewer use whatever tools it has to read. The pacote and repositorio prompts allow changing no file; the pr prompt allows creating only the answer file the request names. In repositorio mode the reviewer may also run the project's tests and read-only commands; in pr mode, only when that writes nothing in the project. The answer format, and so `import-verdict`, is the same in every mode.

Exit 0, 64 (no base resolvable: a full handoff is needed and the plan has no `**Base:**`; an unknown `--mode`; `--dest` without `--mode repositorio` or without a value; `--pr` or `--qa` without `--mode pr` or without a value; a refused dest or round folder; or bad usage), 65 (also a malformed `--trace`: `handoff.bad_trace`). `data`: `{ file, round, mode, dest }` (`dest` is the absolute export path in repositorio mode, the round folder in pr mode, `null` in pacote mode); in pr mode also `request` and `answer` (absolute paths of `pedido.md` and of the `resposta.md` the reviewer writes).

### import-verdict
`baco import-verdict <ENT-NNN> <file|->` — parses the reviewer's verdict (file or stdin `-`; in pr mode, the verdict a person reviewer stated, on stdin after their confirmation; the agent reviewer's answer goes through `import-pr-verdict`), stores it as `revisao/veredito-NN.md` (original text plus a trailing `<!-- baco:parsed {...} -->` JSON footer: `{verdict, findings, handoff, reviewedHead}`, where `handoff` is the latest `handoff-NN.md` that existed at import time — the one this verdict answers — and `reviewedHead` its recorded head; both null when there was no handoff) and writes one `tarefas/FIX-NN.md` per finding that is not `sugestão`. Exit 0; 1 (verdict unparsable/contradictory: nothing is written); 3 when the round number exceeds `review.external_rounds_max` and the verdict is not `aprovado` (human decision required); 64, 65. `data`: `{ verdict, round, fixes: ["FIX-NN.md"] }`.

### import-pr-verdict
`baco import-pr-verdict <ENT-NNN>` — the automatic import of the agent reviewer's answer in pr mode, so a permission rule can allow it without allowing `import-verdict` (which reads any file or stdin). It takes no file: it reads the latest `revisao/handoff-NN.md` and resolves `.baco/logs/revisao-pr/ENT-NNN-rNN/resposta.md` of that round only. It refuses, writing nothing: no handoff yet (64, `prverdict.no_handoff`); the latest handoff not in the HEAD commit (64, `prverdict.handoff_not_committed`); a round whose handoff the latest imported verdict already answered (64, `prverdict.already_imported`); a missing answer, also when the latest round is not a pr round, so an earlier round's answer never counts (65, `prverdict.no_answer`); an answer older than that round's `pedido.md`, or no `pedido.md` (65, `prverdict.answer_stale`). Then it imports the answer with the same parsing, files and exit codes as `import-verdict` (0, 1, 3). Extra arguments are a usage error (64). `data`: the `import-verdict` data plus `answer` (repo-relative path of the imported file).

### waive-review
`baco waive-review <ENT-NNN> --by <name> --reason <text>` — records the human's decision to go without an external review: writes `<delivery>/revisao/dispensa-revisao-externa.md` (who, date and time in the local time zone with the zone named, `YYYY-MM-DD HH:MM (UTC±HH:MM, <IANA zone>)`, e.g. `2026-11-02 14:10 (UTC-03:00, America/Sao_Paulo)`, the IANA name left out when the runtime does not know it; reason; HEAD sha). First line `<!-- baco:head <sha> -->` (same marker as handoffs); last line a JSON footer `<!-- baco:waiver {"by","date","reason"} -->` that `acceptance-report` reads (`--` escaped as in verdict footers). Running it again overwrites the waiver with the current HEAD. A waiver is valid only while no verdict was imported: with any `veredito-NN.md` in `revisao/`, it is refused (exit 64, `waive.verdict_exists`) and the verdict rules apply. Exit 0, 64 (missing or empty `--by`/`--reason`, malformed ENT, verdict already imported), 65 (delivery not found). `data`: `{ file, by, date, reason, head }`.

### acceptance-report
`baco acceptance-report <ENT-NNN> --target <branch> --trace <file.json>... [--qa <qa.md>]...` — writes `<delivery>/aceite.md` (summary, criteria table, manual checklist, review, risks, agents, and the writer's slot: the last section, heading `O que muda para o usuário` / `What changes for the user`, then `<!-- preencher: redator -->` and `<!-- fim: redator -->`) and decides whether merging to `--target` may proceed. `--trace` is repeatable (one trace per spec): their `cas` are merged and, when the same CA appears in two traces, the worse status wins (proven < pending < uncovered < failed < unknown); their `otherScenarios` are merged by scenario ID the same way (passed < pending < failed). A trace without `otherScenarios` (made before it existed) is read as having none; one whose `otherScenarios` is not a list of objects each with a text `id` is malformed (exit 65, `acceptance.bad_trace`, reason `shape`; `build-handoff` the same). When there are any, a section `Cenários ligados só a regras ou requisitos` / `Scenarios tied only to rules or requirements` follows the criteria table, one row per scenario (scenario, what it is tied to, result). A trace that carries a non-null `filter` field (a per-task trace, limited to some criteria) is refused: exit 65, `acceptance.filtered_trace`, nothing written. Uses the highest-numbered `veredito-NN.md` footer as the verdict.

Review waiver: with no verdict, a `revisao/dispensa-revisao-externa.md` (see `waive-review`) whose recorded head is current (same rule as a verdict's `reviewedHead`, R26 below) replaces the blocker `merge.no_verdict` by the warning `merge.review_waived`; the summary says the review was waived by whom and when, and the review section says `Sem revisão externa, por decisão de <by> em <date>: <reason>.` (en: `No external review, by decision of <by> on <date>: <reason>.`). A waiver whose head is not current does not count: `merge.no_verdict` stays and the blocker `merge.waiver_stale` is added (the review section also says the waiver is for another version of the code). Once a verdict exists, any waiver is ignored.

Writer text: when `aceite.md` already exists, what the writer role filled in its slot ("O que muda para o usuário" and any "Se der errado") is carried into the new report, between the two markers, and the line `acceptance.writer_kept` says so (`data.writerKept: true`). The slot is the last section the engine writes, so everything after its heading counts as the writer's text, minus the marker lines; this also reads reports written before the closing marker existed and writers that replaced the opening marker by their text. With no slot heading, or nothing written in it, the slot is left empty, as before.

Risks section: besides pending tests, non-`sugestão` findings of the verdict and orphan tests, it lists the open items of `<delivery>/progresso.md` (see File formats, Progress log): one line per row whose `Situação` is not `resolvida`, `Pendência <ID>: <Pendência> (impacto: <Impacto>; destino: <Destino>).` A missing file, section or table adds nothing. Orphan tests (shown as tests with an unknown identifier) are the traces' `orphanTests` minus any test with an ID known to the delivery: a definition of a plan spec, a scenario of its QA file (`<spec dir>/../qa/cenarios-qa-spec-<name>.md`) or a criterion or scenario in any of the traces. So traces made without `--delivery` do not list the other specs' tests either.

Agents section (`## Agentes`): from `<delivery>/custo.md` (Cost table), one line per distinct (agent, model, effort, harness) in first-seen order with its number of rows, e.g. `- task-reviewer: sonnet, high (8 execuções)`, or `- pr-reviewer: <modelo> no codex, high (1 execução)` when the row names a harness. Without `custo.md` the section says the agents were not recorded.

Blockers:
- verification failures: no criteria in the traces (`merge.no_criteria`), any CA `failed` or with an unknown status (`merge.failed`), any `uncovered` (`merge.uncovered`), any scenario of `otherScenarios` `failed`, `manual_fail` or with an unknown result (`merge.scenario_failed`);
- review: no verdict (`merge.no_verdict`, unless a current review waiver exists; a stale waiver adds `merge.waiver_stale`), verdict not `aprovado` (`merge.verdict_not_approved`), verdict `reviewedHead` missing or not current (see provenance; `merge.stale_verdict`);
- provenance (R19): any trace whose `head` is missing or not current (`merge.stale_trace`); any trace whose `delivery` is not this ENT (null counts as different: `merge.trace_other_delivery`). A recorded head (trace `head`, verdict `reviewedHead`) is current when it equals HEAD, or when it is an ancestor of HEAD and `git diff --quiet <head> HEAD -- . ':(exclude)<docs_root>/entregas/**'` (plus one `':(exclude,glob)<path>'` per `provenance.ignore` entry present both in the config at the recorded head and in the current config: an entry added after the head, even in an uncommitted config, never hides what changed after it; a config at the head that is missing or unreadable counts as an empty list) finds no difference — commits that touch only delivery artifacts (verdicts, `aceite.md`, handoffs) or ignored paths (e.g. a run log committed by an automatic sync) do not make it stale (R26). The same rule applies to the trace `head`, the verdict `reviewedHead` and the waiver head. `provenance.ignore` affects only this freshness check: `build-handoff` still shows those paths in the review diff. When git refuses the diff only because of an ignore entry (the same diff without the entries works), the command stops with exit 65 and `acceptance.provenance_ignore_failed`, naming `provenance.ignore`, instead of marking every head stale; any other git error makes the head not current;
- plan coverage: the plan's `**Specs:**` is empty (`merge.no_plan_specs`), or a plan spec path is not matched by any trace's `spec.path` (`merge.spec_not_traced`; the paths are in `data.specsNotTraced`);
- pending items per the `manual_pending` rule for the target (`block` -> blocker; `warn` -> warning; `ignore` -> skipped; any other value blocks). Pending = scenarios with result `manual_pending`, or automated ones `not_run`/`skipped`, of a CA or of `otherScenarios` alike: a pending manual scenario tied only to a rule follows the same rule as one of a criterion (by default it blocks the merge to `main` and warns elsewhere), enters the manual checklist and the risks. Traces made before `otherScenarios` existed have none, and nothing changes for them. A `manual_pending` scenario flagged `specialist: true` is never pending in this sense (whatever the rule and the target, `main` included): it is not in `merge.manual_pending`, the manual checklist, the summary or the risks; it gets the warning `merge.specialist_pending` (naming the scenarios) and its own section after the manual checklist, `Fica com QA especialista` / `Left for specialist QA`, one line per scenario, `- <ID>: <title> (<kind>)` (title from `--qa` and kind when known). A specialist scenario that was run (`manual_ok`, `manual_fail`) counts like any other. The function `pendingItems(trace)` (exported) returns `{ manual, auto, specialist: [{id, kind}] }`.

Warnings (never block): `merge.manual_pending` / `merge.not_run` under a `warn` rule, `merge.review_waived` and `merge.specialist_pending`.

The Prova column shows, for manual evidence, where, when and in which delivery the test was run. `--qa` only supplies scenario titles for the checklist. Exit 0 (allowed), 1 (blocked by a verification failure: `merge.failed`, `merge.uncovered` or `merge.no_criteria`), 2 (blocked by any other blocker: human gate), 64, 65 (delivery missing; plan missing; malformed trace; filtered trace). `data`: `{ allowed, blockers[], warnings[], specsNotTraced? }` (message keys).

### merge-check
`baco merge-check <ENT-NNN> --target <branch> [--pr <number>] [--json]`: says whether the delivery branch `baco/ENT-NNN` may join `--target` with no person (with `delivery.integration_merge: auto`, the conductor then runs `before_pr` and the integration merge alone). It writes nothing. Read-only checks, each reported as `{key, ok, detail, reason}` (`detail` is the localized sentence, `reason` the last part of its message key `mergecheck.<key>.<reason>`), in this order:

- `battery`: the stamp `.baco/logs/bateria-completa.json` of `run-tests` at the repo root exists and is readable (`no_stamp`, `unreadable`), ran with `dirty: false` (`dirty`), its `head` exists (`missing_head`), no code changed from it to the tip of `baco/ENT-NNN` (`git diff --quiet <head> <tip> -- . ':(exclude)<docs_root>/entregas/**' ':(exclude,glob)**/*.md'`: delivery records and Markdown files anywhere never count, `code_changed`), the target exists (`target_missing`) and its tip, and `origin/<target>` when that remote ref exists, is an ancestor of the delivery tip (`target_moved`); and every layer passed, or each failure of a failed layer is covered by a later `reruns` entry of that layer with exit 0 whose args name the failure's file (same path, or one a path suffix of the other; a `:line` suffix ignored). A failed layer that listed no failure cannot be covered (`failed`). Covered failures make it ok with `ok_flaky` and are listed in `data.flaky` (`[{layer, name, file}]`): pending items, "falha instável".
- `verdict`: the highest `revisao/veredito-NN.md` still describes the code (its `reviewedHead` passes the same freshness rule as `acceptance-report`, R26, against the delivery tip: `stale`) and is `aprovado` (`approved`), or is another verdict for which `progresso.md` records the person's choice to proceed at exit 3 (`exit3`): a line under `## Decisões registradas` that names exit 3 (`saída 3` or `exit 3`, accents and case folded) and that verdict file (`veredito-NN`); otherwise `not_approved`. With no readable verdict, a waiver (`baco waive-review`) counts while current (`waived`, `waiver_stale`); nothing: `none`. A `provenance.ignore` entry git refuses exits 65 (`acceptance.provenance_ignore_failed`).
- `manual`: the `manual_pending` rule for the target (`ignore` or `warn`: ok, `not_blocking`; anything else blocks, as in `acceptance-report`). Under a blocking rule, the traces `revisao/trace-*.json` of the delivery are merged as in `acceptance-report` and no manual scenario may be `manual_pending` and no automated one not run (`pending`, listing them). Specialist scenarios never count. No trace: `no_trace`; an unreadable or filtered one: `bad_trace`.
- `waiting`: the table under `## Esperando a pessoa` of `progresso.md` has no row whose Situação does not start with `resolvido`/`resolvida` (`open`, listing the Item cells). No file or section: ok.
- `ci`: without `--pr`, not ok (`no_pr`, "CI não conferido"). With it, `gh pr view <n> --json headRefOid,statusCheckRollup` (binary from env `BACO_GH`, default `gh`; run at the repo root, 60 s limit). gh missing, failing or answering something else: `gh_failed` with its last stderr line, never a crash. The PR head must be the delivery tip (`head_mismatch`). A failed check (a check run completed with a conclusion other than success, skipped or neutral, or a status context in failure or error): `failed`; one not completed (or a status pending or expected): `running`, "CI ainda rodando"; at least one success and nothing else: `ok`. When the tip has no check that ran (the CI ignores Markdown), the first-parent history is walked back from the tip (at most 50 commits): each earlier commit's check runs come from `gh api repos/{owner}/{repo}/commits/<sha>/check-runs`; the first commit with checks decides (`failed`, `running`, or `ok_markdown`, naming that commit), provided every commit after it, the tip included, changes only `*.md` files against its first parent; a commit that changes something else and has no check: `not_run`; nothing found: `no_checks`.
- `policy`: the target is `branches.integration` and `delivery.integration_merge` is `auto` (otherwise `ask`; the default is `ask`). The target `branches.main` is never ok (`main`, "a junção na principal sempre pede a pessoa"); any other branch: `other`.

Warning `battery.ci_timeout_near` (never blocks) when `test_runs.ci_full` is `merge` (the default) and the stamp's `seconds` is above 70% of the largest `timeout-minutes` found in `.github/workflows/*.yml` / `*.yaml`. Human output: one line saying clean or how many conditions need the person, one line per condition (`ok:` or `NÃO:`), then the warning. Exit 0 when every condition is ok, 2 when any needs the person, 64 usage (bad id, no `--target`, `--pr` not a positive integer), 65 delivery folder not found or ambiguous, branch `baco/ENT-NNN` missing (`mergecheck.no_branch`), git failure. `data`: `{ delivery, target, branch, tip, ok, conditions, warnings, batterySeconds, ciTimeoutMinutes, flaky }` (`batterySeconds` and `ciTimeoutMinutes` always present, null when unknown).

### cost
`baco cost add <ENT-NNN> --phase <n> --agent <name> --model <m> --effort <e> [--harness <h>] [--turns n] [--tokens n] [--seconds n] [--note s]` appends a row to `<delivery>/custo.md` (created on first use). `--harness` names the AI tool the run happened in (for example `claude-code`, `codex`, `opencode`); without it the row records `—`, so calls written before it still work; an empty value exits 64. `baco cost summary <ENT-NNN>` totals by phase and by model, and by harness when any row names one. Numbers must be non-negative integers or `—`/omitted (stored as `—`, counted as 0; the summary reports runs with unknown tokens). Exit 0, 64 (missing flag, bad number), 65 (delivery missing; summary with no `custo.md`). `summary` `data`: `{ byPhase, byModel, byHarness, total }` each `{turns, tokens, seconds, runs}` (`byHarness` keys rows without a harness as `—`), plus `measured` (below; `null` without a measured section). `baco cost summary` with no delivery totals the whole project: each stage of `<docs_root>/custo-projeto.md` and the measured section of each delivery's `custo.md`, one row per stage or delivery and the sum (exit 1 when nothing is measured yet). `baco cost summary --project` totals `<docs_root>/custo-projeto.md` by stage (`data.measured.byLabel`; 65 when the file is missing).

`baco cost history [--json]` gives one row per delivery (folders `<docs_root>/entregas/ENT-NNN-*`, in name order) whose `custo.md` has a measured section (all its stages summed), for the planner's estimate. Tokens (`Total` of the measured rows) are split by `Quem` (a `baco:` prefix dropped, `_` read as `-`): `conductor` (`condutor`), `implementers` (`implementer*`, `backend`, `frontend`), `reviewers` (`task-reviewer`, `final-reviewer`, `pr-reviewer`, `simplifier`, which also covers a harness call recorded by `harness-answer --agent <role>`) and `others` (everything else: planner, auditors, `exec`, `avulsa`, `sessão`, whose role cannot be told). Counts from the delivery folder: product tasks (`tarefas/T-*`), `INT-*`, `FIX-*` and `CI-*` tasks (distinct names, extension dropped), task reviews (`revisao/<TASK-ID>-revisao-NN.md`), final review rounds (distinct NN of `revisao/revisao-final-NN[-<part>].md`, so a round split by part counts once) and PR rounds (`revisao/veredito-NN.md`). Ratios, rounded to whole tokens, `null` when the count is 0: `conductorPerTask` (conductor / all tasks), `builderPerReview` (implementers / task reviews), `reviewerPerReview` (reviewers / task reviews + final rounds + PR rounds). The text output is a table, plus a line `Todas` when there are several deliveries. Exit 0, 1 (no delivery measured yet: `cost.history_none`), 64 (an extra argument). `data`: `{ deliveries: [{ ent, folder, tokens: {total, conductor, implementers, reviewers, others}, counts: {tasks, int, fix, ci, taskReviews, finalRounds, prRounds}, ratios: {conductorPerTask, builderPerReview, reviewerPerReview} }], total }` (`total`: the same shape without `ent`/`folder`, from the sums; `null` when none).

`baco cost measure [<ENT-NNN>] [--since <t>] [--until <t>] [--session <id>]... [--claude-dir <dir>]... [--codex-dir <dir> | --no-codex] [--opencode-db <file> | --no-opencode] [--conductor-harness <claude-code|codex>] [--write [--label <stage>]]` reads the real token usage from the session transcripts, never from what an agent reported. Two more sources, both optional: the ledger of `baco harness-answer` (`.baco/logs/uso-ferramentas.jsonl` of the main checkout), where each call counts what it added to the largest earlier running total of its harness and conversation (a line written twice adds nothing; `thinking` counts as output; `who` is the recorded `agent`, else `exec`; `--session` matches the conversation id); and OpenCode, `$XDG_DATA_HOME` (default `~/.local/share`)`/opencode/opencode.db`, or `--opencode-db`, read-only with `node:sqlite` (Node 22.5 or newer; otherwise the warning `cost.measure_opencode_unreadable` and OpenCode is left out): assistant messages whose `path.cwd` is inside the project roots (any message of the sessions named by `--session`), each message once, `reasoning` counted as output, `who` `sessão`, or the agent of a session with a parent (a subagent). `sources` gains `tools: {calls}` and `opencode: {sessions, unreadable}`; a given `--opencode-db` that does not exist exits 65. Times are `AAAA-MM-DD`, `AAAA-MM-DD HH:MM` (local, as `date` prints it) or ISO with a zone; a date or time that does not exist (`2026-02-30`, `24:00`, `12:60`) is a bad time. Window: `--since`/`--until` (until defaults to now, and the window really ends there); with a delivery and no `--since`, the plan's `**Início:** AAAA-MM-DD HH:MM` line, else the time of the first commit that touched the delivery folder; `--session` (repeatable) keeps only those conversations (a Claude Code session id or a Codex session id) and, alone, needs no window. Sources, read only when this command runs: Claude Code, `$CLAUDE_CONFIG_DIR` (default `~/.claude`)`/projects/<path>/`, for the project root and each of its git worktrees, `<path>` being the folder with every character other than a letter or a digit turned into `-` (conductor: `<session>.jsonl`; subagents: `<session>/subagents/agent-*.jsonl`, with the agent type from `agent-*.meta.json`); Codex, `$CODEX_HOME` (default `~/.codex`)`/sessions/**/*.jsonl`, only sessions whose `cwd` is inside the project or one of its worktrees, on directory boundaries (a Windows path compared with either separator and without case; any session with `--session`). The worktrees are those git lists now, those recorded by an earlier measurement in `.baco/logs/custo-fontes.json` (folder paths only, of this machine; written only when git ignores it, else a warning asks to ignore `.baco/logs/`), and, for Claude Code, any `<path>` of a `.worktrees/<TASK-ID>` folder of the project: a measurement after `cleanup-branches` still finds the tasks' conversations. A response is counted once, with the largest value of each number among its lines (usage written again while it streams only grows): Claude Code by message id (one response is often written on several lines), Codex by `response_id` of `token_usage_record`, or, in older files, by the `token_count` events whose running total moved; a file with both counts its `token_count` events only before its first record (once per move of the running total), minus the last of them when it has the record's usage and no new turn lies between them. Synthetic messages, lines outside the window and files last changed before it are skipped; lines that are not JSON are skipped and counted. Codex `input_tokens` include the cached part; the row splits them like Claude Code (`Entrada` without cache, `Cache lido`). Who: Claude Code's main file is the `condutor`; a subagent transcript is its agent type; a Codex `exec` session is `exec`, a Codex subagent its kind. A main session (Claude Code's own file, or a Codex session that is not `exec` or a subagent) is the `condutor` only when its harness is the conductor's (`--conductor-harness`, default `claude-code`); a main session of the other harness (for example a Codex session opened only to write a file) is `avulsa`, counted with its harness and never as the conductor. Output groups: `Condutor (Claude)`, `Subagentes (Claude)` (the conductor harness's roles) and each other harness on its own (`Codex`). Conductor rows are grouped by their own harness, so a `custo.md` measured before `avulsa` existed, with conductor rows of two harnesses, shows one conductor group per harness (the conductor total still sums them). Per conductor session (labels `condutor-1`, `condutor-2` in order of first response in the window, never an id): responses in the window of all its responses, tokens and largest context. A conversation owns the window when at least half of its responses fall inside it (when none does, the one with the most responses inside): a handoff to a new conversation overlaps the old one for minutes, so tokens of every conversation in the window are summed, but `Maior contexto` of the stage and of the conductor rows comes only from the owning conversations. `Maior contexto`: the largest input plus cache read plus cache written of one conductor response. `--write` writes the section above, replacing the rows of the same stage: the delivery's `custo.md` (stage `entrega` unless `--label`; created with an empty ledger when missing) or, without a delivery, `<docs_root>/custo-projeto.md` (`--label` required). Only numbers, model names, agent types, the stage and the window are written: never text, ids or paths from a transcript. Two deliveries measured over overlapping windows count the same conversations twice; use `--session` then. Exit 0, 1 (nothing found: the folders read are named), 64 (no window or session, bad time, `--write` without `--label` outside a delivery), 65 (a folder given does not exist; delivery missing). `data`: `{ ent, since, until, sessions (the `--session` ids given, `[]` without), rows[{harness, model, who, responses, input, cacheRead, cacheWrite, output, total, maxContext}], total, conductor (with maxContext), subagents, conductorShare (0 to 1), byHarness, byModel, conductorHarness, groups[{kind: conductor|subagents|harness, harness, ...totals}], conductorSessions[{label, harness, who, responses, totalResponses, share, owner, total, maxContext, firstAt, lastAt}], skippedLines, sources, written?, label? }`. `baco cost add` prints a message and returns `created` (the path) when it creates `custo.md`.

### run-tests
`baco run-tests (--layer <name>... | --all) [--quick] [--verbose] [-- <extra args>]` and `baco run-tests --smoke` — runs the configured test commands the way agents should run them. Meant for: during a task, `--layer <the task's layers> --quick -- <the task's test files and touched files' tests>`; `--all` (every browser, no `--quick`) once per delivery, after the last external verdict `aprovado` (or the current waiver, or the recorded exit-3 decision) and before the acceptance report, plus again only when `merge-check` says its stamp no longer holds; the external rounds run on the task tests and the PR's CI quick battery.

- Layers: `--layer` is repeatable or a comma list; `--all` is every layer of `tests` in config order (plus, with `--quick`, the layers that exist only in `tests_quick`). The command is `tests_quick.<layer>` with `--quick`, falling back to `tests.<layer>`. Unknown layer, layer without a string command, no layer configured, both or neither of `--layer`/`--all`: exit 64.
- Execution: at the repo root, through `sh -c`, in its own process group, stdin closed (an interactive prompt fails instead of hanging). When the shell exits, processes it left running in its group get SIGTERM (a leaked dev server does not hold the port for the next run), and SIGKILL if any is still there 2 s later; the run ends when the output pipes have drained and the group is empty, or at the end of those 2 s. Extra args after a bare `--` are shell-quoted and appended to the command (e.g. to run only some files); with more than one layer they are refused (64). Progress lines (`[baco] ...`: the command being run, waits, warnings) go to stderr as they happen.
- Output and summary: by default the child's stdout and stderr are not printed; they are written in full, interleaved as they arrive, to a new file per layer, `.baco/logs/run-tests-<UTC time>-<pid>-<layer>.log` under the repo root (the folder is created; nothing is ever deleted). The summary on stdout says, per layer, passed or failed; for a failed layer, the failing tests (status failure or error) of the JUnit files the layer created or updated, one entry each with the file (or classname) and its whole message (the JUnit `message` attribute, up to 20 lines, the rest counted and left to the log), at most 20 tests plus a count of the rest; when none can be read from JUnit, the last 20 lines of the output instead; then the log path. If `git check-ignore` says `.baco/logs/` is not ignored, a warning suggests adding it to `.gitignore`. If the log file cannot be created, a warning says so and that layer's output is passed through as before. `--verbose` restores the old behavior: output passed through to stdout/stderr, no log and no failure lines. `--verbose` cannot be combined with `--smoke`.
- `.baco/local.env`: per-machine settings (e.g. `PLAYWRIGHT_BROWSERS_PATH`), `KEY=VALUE` lines, `#` comment lines, optional `export ` prefix and surrounding quotes, no expansion. Its vars are passed to the child on top of `process.env` (they win over any variable, `PATH` included; the file is not versioned, so `guard-tests` does not see it: it is trusted like the machine's own shell profile). Read from the repo root; when the root is a linked worktree (a task folder) with no file of its own, the file of the main checkout is used (`git rev-parse --path-format=absolute --git-common-dir`, its parent folder), since a git-ignored file is never copied into worktrees; a file in the worktree wins. If the file exists and `git check-ignore` says it is not ignored, a warning suggests adding it to `.gitignore`; unparsable lines are reported and skipped (the main checkout's file is then named by its full path).
- Queue: layers in `tests.queue` (default: names starting with `e2e`) take a machine-wide lock before running: an atomic `mkdir` of `/tmp/baco-queue/baco-test-queue.lock` (under the shared `/tmp`, not `os.tmpdir()`, so users and sessions with their own `TMPDIR` share one queue; `os.tmpdir()` where there is no `/tmp` or where a sandbox makes it read-only, as Claude Code's does; `BACO_QUEUE_DIR` overrides both) with `owner.json` (`pid`, `root`, `layer`, `started`, `token`). The folder `/tmp/baco-queue` is created by the engine and set to 0777 without the sticky bit (a failed chmod is ignored: another user's folder, already open), so any user can take over a dead lock left by another user (in the sticky `/tmp` only the owner could move it). `BACO_QUEUE_DIR` replaces the folder: created and opened the same way when missing, left as it is when it exists. If a live pid holds the lock, one line says which project/layer it waits for and it polls (every `BACO_QUEUE_POLL_MS`, default 2000) until free; a lock whose pid is dead (or a lock dir without owner file older than 30 s) is taken over. If that takeover is refused (EPERM/EACCES: e.g. the folder is not open to this user), the command stops at once with exit 65 and one message naming the lock folder to remove (`runtests.queue_stale_locked`), instead of waiting the whole timeout; if the lock cannot be created in the folder at all (permissions, or the folder is a file), likewise exit 65 naming the folder (`runtests.queue_base_blocked`). The lock is released after each layer, on exit and on SIGINT/SIGTERM/SIGHUP (which also terminate the running command's group; the process then exits 128+signal). `BACO_QUEUE_TIMEOUT` (seconds, default 3600, `0` = do not wait) bounds the wait: on expiry the command stops with exit 65 (`runtests.queue_timeout`, naming the holder) and the remaining layers do not run. While it waits, the run lists itself in the folder `waiting/` next to the lock (`/tmp/baco-queue/waiting/<pid>-<token>.json`: `pid`, `root`, `layer`, `since`; the folder is created 0777 like the queue folder), and removes the file when it gets the lock, times out, fails or exits (also on a signal). The entry is written to a temporary name in the same folder (not ending in `.json`) and renamed in, so a reader never sees it half written. Writing it is best effort: the queue works without it. `queue-status` shows that list.
- JUnit: the mtimes of `*.xml` in `tests.junit_dir` are recorded before each layer; if no XML was created or updated, a warning says the layer wrote no JUnit report (the engine cannot see those tests).
- Battery stamp: `--all` without `--quick` and without extra args writes `.baco/logs/bateria-completa.json` at the repo root (replacing the previous one), read by `merge-check`: `{at, head, branch, dirty, seconds, passed, layers: [{layer, exit, seconds, failures: [{name, file}]}], reruns: []}`. `head` and `branch` are taken before the first layer; `dirty` is true when `git status --porcelain --untracked-files=all` shows changes to code at that moment, where code is everything except `<docs_root>/entregas/**`, Markdown files anywhere (`**/*.md`), `.baco/logs/` and `tests.junit_dir` (when git cannot tell, true); `seconds` is the whole run, queue waits included; a layer that did not run (queue or spawn error, exit 65) is recorded with `exit: null`; `passed` is true only when every layer exited 0. `--layer <l> -- <files>` (one layer, extra args) without `--quick`, when the stamp's `head` is the current HEAD and the tree is not dirty (same rule), appends `{at, layer, args, exit}` to the stamp's `reruns`: the re-run of tests that failed. Neither is written with `--quick`, with `--layer` and no extra args, or when HEAD cannot be read. Messages `runtests.stamp_written` / `runtests.rerun_recorded`; a write failure is a warning (`runtests.stamp_failed`) and does not change the exit code.
- Exit: 0 when every layer exited 0; 1 when any failed (non-zero exit or killed by a signal; the next layers still run); 65 when the shell could not be spawned, the queue wait timed out or the queue is blocked (stops there); 64 usage. `data`: `{ runs: [{layer, quick, command, exit, junitWritten, seconds, waitedSeconds, output, log, failures}] }` (`command` includes the extra args; `exit` is null when killed by a signal; `output` is the last 16000 characters of stdout+stderr with `--json`, where the child output is captured instead of printed, and null otherwise; `log` is the repo-relative path of the full-output log, null with `--verbose` or when it could not be written; `failures` is `[{name, classname, file, message}]` read from the JUnit files the layer wrote, `[]` when none failed or none was written).
- `--smoke`: runs `app.smoke` with the same env and stdin rules, no queue, no JUnit check and no log (its output is passed through, or captured with `--json`, as before), with a time limit (`BACO_SMOKE_TIMEOUT` seconds, default 300; on expiry the process group gets SIGTERM, then SIGKILL after 3 s). Exit 0 ok, 1 failed (`runtests.smoke_failed`) or timed out (`runtests.smoke_timeout`), 64 when no `app.smoke` is configured, 65 when the shell cannot be spawned. `data`: `{ smoke: {command, exit, timedOut, seconds, output} }`. `--smoke` cannot be combined with `--layer`, `--all`, `--quick` or extra args.

### queue-status
`baco queue-status [--json]` — shows the machine-wide test queue of `run-tests` (`BACO_QUEUE_DIR` respected), from any folder (no git repo needed); it creates nothing, but it does clean up the waiting list (see below): who holds the lock (project root, layer, since when as local `HH:MM`, pid; a lock whose pid has ended is shown as abandoned, which the next run takes over by itself) and which runs are waiting for it, oldest first. Waiting entries of processes that have ended are skipped and removed; unreadable ones are skipped, and removed only when older than 10 s (a younger one may be another run's entry being written). Text in pt-BR or en per `language` (the default pt-BR outside a repo). Exit 0; 64 with any positional argument. `data`: `{ lock: {pid, root, layer, started, alive} | null, waiting: [{pid, root, layer, since}] }` (`started`/`since` ISO 8601).

Argument parsing: a bare `--` ends the options for every command; what follows is passed to the command verbatim (only `run-tests` uses it).

### Plugin hook `write-guard` (uses `scripts/lib/shellwrites.mjs`)
A `PreToolUse` hook on the shell tool (Claude Code: Bash; Antigravity: `run_command`), only for subagents (Claude Code: `agent_id` in the input; Antigravity: a transcript whose first line is a system message sent by another conversation, see `hooks/host.mjs`) in a BACO project: it denies a command that writes by redirection (`>`, `>>`, `>|`, `&>`, `&>>`, `<>`, `N>`, `>& file`) or `tee` to a file outside the project (the git work tree of the command's folder and, from a linked worktree, the main work tree). It is a guard against an agent's accidental writes, not a security boundary. It reads quotes, escapes, comments, heredocs, `$( )` and backticks (also inside double quotes), process substitution, `$(( ))`, `(( ))`, `[[ ]]` and the options of common wrappers (sudo, env, timeout, nice, nohup, stdbuf, command, exec, xargs, time). The destination is followed through symlinks component by component (a dangling link too) before `..` applies; `/dev/*` is allowed only when reached without `..`. Allowed because it cannot be placed without running the shell: a target with a variable, a command substitution or an unquoted wildcard, an unquoted `~user`, and a relative target after a `cd`, `pushd` or `popd` of the same shell earlier in the command (one inside `$( )`, backticks or a closed `( )` subshell does not count), or a file given to a `tee` wrapped by `env -C` or `sudo -D` (which move only the wrapped program, not the shell's redirections). Known gaps: `sh -c` and `eval` strings, aliases and functions, expansions inside heredoc bodies, and files that programs write by themselves (`cp`, `dd of=`, `node -e`). Fails open on any error.

## File formats

### IDs
`(RF|RNF|RN|INV|CA|CT|QA|P|ADR)-` + optional capability `[A-Z]{2,6}-` + exactly 3 digits: `RF-001`, `RF-EMP-001`, `CT-EMP-022`. Shorthand refs are expanded: `RF-EMP-001/007` (list) and `CT-EMP-001–004` / `CT-EMP-001-004` (range, en dash or hyphen); a tail must be exactly 3 digits. Matching of headings and labels is accent- and case-insensitive; CRLF is accepted.

### Spec
Definitions of RF/RN/RNF/INV/CA are recognized as headings (`### RF-001 | title`), bullets whose ID is followed by `|`, `:` or the end of the line (`- **RF-EMP-001 | title:** text`, `- RF-EMP-001: text`), or table rows. The first cell of a row is the ID alone (`**CA-EMP-001**`) or the ID followed by a title (`**CA-EMP-001** Title`, `CA-EMP-001 — Title`, `CA-EMP-001: Title`); the titled form counts only in a definition table. A table row defines an ID only in a table whose first header is `ID`, or that has Dado/Quando/Então columns; rows of traceability/matrix/coverage tables (headers `Origem`/`Verificação`, or under a heading containing "rastreabilidade", "matriz", "cobertura", "histórico", "disposição", "obsoleto", "aposentado", "retirado", "descontinuado", "history", "retired", "deprecated" or "superseded") are references, not definitions. A row of any other table still defines an ID that is defined (or retired) nowhere else.
Retired IDs: a table row whose status starts with a retirement word (`obsoleto`, `substituído`, `revogado`, `retirado`, `removido`, `descontinuado`, `aposentado`, `cancelado`, or `obsolete`, `superseded`, `replaced`, `revoked`, `retired`, `removed`, `withdrawn`, `deprecated`, `cancelled`, any gender or number, backticks and bold ignored) records a retired ID: it is not a definition, references to it are not dangling, and defining it again is `RETIRED_ID_REDEFINED`. The status is read from the columns whose header starts with `Situação`, `Status`, `Estado`, `Disposição`, `State` or `Disposition`; a table with none of those that is not a definition table is read on every cell after the ID (in a definition table without such a column, a cell like "removido da lista" in `Então` retires nothing). A status that also says `parcial`, `em parte` or `partial` keeps the ID in force: such a row is a reference, never a definition nor a retirement. Metadata: a table row whose first cell starts with "Código" (`Código`, `Código da spec`, `Código / domínio`; the value is its first token, so `IDC / Identidade` gives `IDC`) and a `| Versão | Y |` row, or bullets `- **Código:** X`, `- **Versão:** Y`. History: a table with `Versão` plus `Alteração|Descrição|Mudança` columns (or any table with `Versão` under a heading containing "histórico"), or bullets under that heading. The last history row must match the metadata version.

Next free numbers: an optional metadata row `| Próximos números livres | RF-XYZ-016, RN-XYZ-021, CA-XYZ-042 |` (or the bullet `- **Próximos números livres:** ...`; label matched without accents or case) holds, per series, the highest number ever used plus one. Values are split on commas, semicolons and spaces; backticks and bold are ignored. A value of a series the engine does not know (`DEC-XYZ-011`, `RIS-XYZ-005`) belongs to the project and is accepted unchecked. `nextFree.declared` maps each series to the value read (`null` when the row is absent); `nextFree.minimum` maps each series the spec defines or retires (with its code) to the highest number in the file plus one, a lower bound since numbers used only in earlier versions are not in the file. All findings are warnings at the row's line, and only when the row exists: `NEXT_FREE_STALE` when a defined or retired ID has a number equal to or above the value of its series (`series`, `max`, `declared`, `minimum`; a number may be reused); `NEXT_FREE_MISSING_SERIES` when a series the spec defines or retires is not in the row (`series`, `max`, `minimum`); `NEXT_FREE_INVALID` for a value that is not an ID of the spec's code, repeats a series or has the wrong shape (`value`). The row's IDs are not citations, so they never make `NO_DEFINITIONS`. The QA file is not checked (there is no command that validates it).

### Catalog (`<docs_root>/catalogo-de-specs.md`)
A Markdown table whose headers include `Código` and `Implementação`. Engine-managed columns, inserted right after `Validação` when first written:

| Column | Content |
|---|---|
| `Versão implementada` | `2.1 @ abc1234 (ENT-003)` — spec version, `@`, sha (stored as 7 chars), optional delivery in parentheses; `—` when empty |
| `Versão validada` | free text, usually a spec version; `—` when empty |

`Implementação` states: `não iniciada`, `em implementação`, `implementada`, `não verificada`. `Validação` states: `pendente`, `parcialmente validada`, `validada`, `validada sem revisão externa`, `não conforme`. The sha parsed from `Versão implementada` is the baseline for `spec-diff --base auto`.

### QA scenarios file
Each scenario is a heading starting with its ID (`### CT-EMP-001 | title`). Bullets under it (`- **Label:** value`):
- `**Contratos:**` CA/RF IDs the scenario proves (shorthand allowed).
- `**Automação:**` first word is `automatizado`, `manual` or `pendente`; an automated scenario names its tests in backticks (`` `tests/x.test.ts` ``), one or several on the same line. Every backticked text with a `/` or ending in a file extension is a test path (spaces inside are kept) (`testRefs`, in order; `testRef` is the first, kept for older readers), so a backticked word such as `` `regra` `` is not one. The same line may declare the test layer: the word `regra` or `navegador` (backticked or not, case and accents ignored, outside the test paths; both or neither -> `layer: null`). Without a JUnit match, a latest evidence row `reprovado` yields `manual_fail` whatever the automation (a rejection is never read as "not run"); otherwise `automatizado` yields `not_run`, and any other scenario takes its result from the evidence table (none -> `manual_pending`).
- Specialist scenario: `**Automação:** manual, especialista`, optionally with its kind, `manual, especialista: leitor de tela` (the word `especialista`, case and accents ignored, on a `manual` line; backticks and bold ignored). `readQa` gives `specialist: true` and `specialistKind` (the text after `especialista:` up to `;`, `(` or the end, trimmed; `null` when none); every other scenario has `specialist: false, specialistKind: null`. Only a specialist QA runs it: it is never asked to the person and never blocks a merge (see `acceptance-report`). The planner marks the kinds listed in `qa.specialist`.
- A table row `| Versão da spec | 2.1 |` records the spec version the file was written against.

Evidence table (heading `Evidências de execução`), appended by `qa-evidence`:

```
| CT | Resultado | Data | Onde | Entrega |
|---|---|---|---|---|
| CT-EMP-001 | aprovado | 2026-10-28 | staging, Chrome | ENT-003 |
```
`Resultado` is `aprovado` or `reprovado`; the latest row by document order (lowest in the file, across all evidence tables) per CT wins. `trace --delivery` only considers rows whose `Entrega` is that delivery.

### Test-ID convention
Tests are linked to scenarios/criteria by IDs inside square brackets in the test title (JUnit `testcase name`): `it('[CT-EMP-001] rejects duplicate CNPJ', …)`, `[CA-EMP-004]`. Several IDs may share one bracket or use several. IDs outside brackets are ignored. A JUnit case with bracketed IDs matching nothing known (to the spec and QA file given, plus, with `trace --delivery`, every spec of the delivery) is listed in `orphanTests`. Parsed JUnit handles nested `<testsuites>`, entities, self-closing `<testcase/>`, `<skipped/>`, `<failure>`/`<error>` (both = failed).

### Delivery folder
```
docs/entregas/ENT-NNN-<slug>/
  plano.md              plan; header below
  tarefas/FIX-NN.md     fix tasks created by import-verdict (other task files live here too)
  revisao/handoff-NN.md reviewer packets, or in repositorio mode the pointer to the exported copy (first line: <!-- baco:head <sha> -->)
  revisao/veredito-NN.md imported verdicts (with <!-- baco:parsed {verdict, findings, handoff, reviewedHead} --> footer)
  revisao/dispensa-revisao-externa.md  external review waiver (waive-review; first line <!-- baco:head <sha> -->)
  progresso.md          progress log; its "Pendências" table feeds the acceptance risks
  custo.md              cost ledger, and the usage measured from the transcripts (cost measure --write)
  aceite.md             acceptance report
```
`ENT-NNN` resolves by prefix `ENT-NNN-`; zero or several matching folders exit 65. Numbers are two digits and keep growing past 99; they are always compared numerically (`handoff-100` comes after `handoff-99`).

### Plan header (`plano.md`)
Two bold-label lines (colon inside or outside the bold; first occurrence wins):
```
**Specs:** docs/specs/spec-empresas.md@2.1, docs/specs/spec-autenticacao-sessao.md@1.4
**Base:** 3f9c2ab
```
An optional third line, `**Início:** AAAA-MM-DD HH:MM` (the time planning started, from `date`), is where `cost measure ENT-NNN` starts its window.

`Specs` is a comma-separated list of `path@version` (paths relative to the repo root; backticks and a trailing period tolerated). `Base` is the git ref the delivery started from. It SHOULD be a commit sha: the handoff diff is two-dot (`Base..HEAD`), so with a moving branch name (e.g. `develop`) the diff would also include unrelated commits made on that branch after the delivery started (or lose changes already merged into it).

### Verdict (reviewer output)
```
Veredito: ajustes

## Achados
- [crítico] src/empresas/service.ts:42 — CNPJ duplicado não é rejeitado
- [importante] — Falta teste para CA-EMP-004
- [sugestão] src/util.ts — nome pouco claro
```
- One `Veredito: aprovado|ajustes|bloqueio` line (first one wins; `#`, `>`, `*`, `_`, backticks and a trailing period around it are accepted).
- Findings are bullets (`-`, `*`, `+`, `1.`, `1)`) under a heading or bare line starting with `Achados` (a count like `(3)` is accepted). Only that section is read.
- Each finding must start with a bracketed severity, `[crítico]`, `[importante]` or `[sugestão]` (accent- and case-insensitive; `**[crítico]**` ok), then optionally `<location> — ` (separator `—`, `–` or `-`; the location must contain `:digits`, `/` or `.`), then text. A bracketed line in the section that does not parse is an error. A bullet in the section without a bracket token whose first word (after stripping bold, brackets and parentheses) is a severity label — `crítico`, `importante`, `sugestão` or `bloque…` (e.g. `- crítico: …`, `- **Crítico** …`, `1. (crítico) …`) — is also an error (`malformed_finding`), so such a verdict is never imported as clean.
- Contradiction rule: `aprovado` with any `crítico` or `importante` finding is rejected (exit 1). `ajustes` and `bloqueio` require at least one finding. `aprovado` may carry `sugestão`s.
- Every non-`sugestão` finding becomes a FIX task.

### Progress log (`progresso.md`)
Free-form, from [`templates/pt-BR/progresso.md`](../templates/pt-BR/progresso.md). The engine reads only the first table under the heading `Pendências` (any level; accent/case-insensitive; up to the next heading of the same or a higher level) that has `Pendência` and `Situação` columns, matched by header name:

```
| ID | Pendência | Impacto | Responsável | Destino | Situação |
|---|---|---|---|---|---|
| P-01 | Limite de upload não definido | arquivos grandes falham | Ana | ENT-002 | aberta |
```

### Cost table (`custo.md`)
```
# Custo | ENT-NNN

|---|---|---|---|---|---|---|---|---|---|
```

### Trace JSON (`trace --out`, input of `acceptance-report`)
```json
{
  "head": "<sha of HEAD when trace ran, or null outside a repo>",
  "spec": { "path": "docs/specs/spec-empresas.md", "version": "2.1" },
  "delivery": "ENT-003 | null",
  "filter": ["CA-EMP-001"] | null,
  "cas": [
    { "ca": "CA-EMP-001", "status": "proven|failed|pending|uncovered",
      "scenarios": [
        { "id": "CT-EMP-001", "via": "qa|direct", "automation": "automatizado|manual|pendente|null",
          "tests": ["tests/e2e/empresa.spec.ts", "tests/unit/empresa.test.ts"],
          "result": "passed|failed|skipped|not_run|manual_ok|manual_fail|manual_pending|layer_mismatch",
          "evidence": { "date": "2026-10-28", "where": "homologação", "delivery": "ENT-003" } } ] } ],
  "otherScenarios": [
    { "id": "CT-EMP-009", "contracts": ["RN-EMP-001"], "automation": "manual", "tests": [],
      "result": "manual_pending", "evidence": null,
      "specialist": true, "specialistKind": "leitor de tela" } ],
  "orphanTests": ["<test name>"],
  "summary": { "proven": 0, "failed": 0, "pending": 0, "uncovered": 0 }
}
```
Layer check: a QA scenario that declares a layer (`layer` in its trace entry, absent otherwise) and has no failed case and no `reprovado` row is `layer_mismatch` when none of its matching cases is of that layer. A case's file is its JUnit `file` attribute, or a `classname` that is a path (has a `/` or ends in a code extension; Playwright and Vitest put the file there, node:test does not); it matches a declared path when equal or when one ends with `/` plus the other. A case's known layer is the one layer whose declared paths (in that QA) match its file; none, or a short name matching paths of both layers, means unknown. A `navegador` scenario needs a case whose known layer is `navegador` (a case with no file, a shared short name, or a QA that declares no `navegador` path cannot show it). A `regra` scenario is refused only a case whose known layer is `navegador`. Without a declared layer nothing changes. Rules: a CA with no scenario is `uncovered`; any `failed`/`manual_fail`/`layer_mismatch` makes it `failed`; all `passed`/`manual_ok` makes it `proven`; otherwise `pending`. `via: "direct"` means a test cites the CA ID itself. When JUnit and a manual `reprovado` evidence both exist, the worse outcome wins. Multiple test cases for one ID aggregate as failed > skipped > passed. `spec.path` is relative to the repo root. `evidence` is the evidence row used for the scenario (`null` when none, and always `null` for `direct`). `tests` (QA scenarios only) lists the test paths of the scenario's `Automação` line; the link to JUnit stays by the IDs in the test titles, so `tests` says which files to read or run, not which results count. `specialist: true` (QA scenarios only, absent otherwise) marks a specialist scenario (see QA scenarios file), with `specialistKind` when the QA line names a kind; the result is computed as for any manual scenario (without evidence it stays `manual_pending`, and its CA stays `pending` in the trace); only `acceptance-report` treats it apart. `acceptance-report` requires `head` to be current (equal to HEAD, or only delivery-artifact commits since) and `delivery` to equal the ENT being accepted; it refuses (exit 65) a trace whose `filter` is a non-empty list.

A trace limited to some criteria carries a non-null `filter` field; `acceptance-report` refuses it (exit 65).

## Known limitations

- `guard-tests` attributes a changed line to enclosing tests by indentation plus a JS-style regex (`it|test|describe(` with optional modifiers). One-line tests, titles split across lines, or other test syntaxes (e.g. non-JS frameworks) can evade it; a tagged test is then not reported. A test whose call has ended before the changed line does not enclose it. Its end is the later of two readings: the balance of the call's parentheses, read past strings, templates, regex literals and comments; and the indentation rule, which skips lines that start inside template text or a block comment (found by a separate simple scanner, without the regex-or-division guess: it reads as a regex only a `/` after `( , = : [ ! & | ? { ;`, `return` or the line start that closes on the same line) and takes the first later line at the opener's indentation or less that starts with `})` or `)`, or with `}` and `,` once the callback has opened on an earlier line (`}, 10000);`), or (ending just before it) one that opens another test or describe or starts a top-level declaration (`function`, `const`, `let`, `var`, `class`). With no end found, the test runs to the end of the file. Taking the later end means a misreading in either one only keeps protection on longer; a helper written after the last test is outside it because both agree.
- `guard-tests` finds the task start by the branch names `baco/ENT-NNN-<TASK-ID>` and `baco/ENT-NNN`; a task branch named otherwise, or a detached head, is compared only with `--base` unless `--task-base` is passed.
- `guard-tests` scans committed changes only (`--base` .. `--head`, default `HEAD`). Uncommitted or staged edits are not seen; commit first.
- Verdict findings must use bracketed severities (`[crítico]`, `[importante]`, `[sugestão]`). A bullet starting with a severity label but no bracket is rejected (see Verdict); findings in other shapes (e.g. a paragraph, not a bullet) are not read; if no finding is parsed, `ajustes`/`bloqueio` is rejected.
- `guard-tests` treats a rename that keeps the last extension (`a.test.js` -> `old/a.test.js`) as a move; if the test runner's own config excludes the new location, the guard does not know it.
- `validate-spec` matches Dado/Dada/Dados/Dadas, Quando and Então as whole words, so the common noun "dados" (data) in a CA text also satisfies the Given part of `CA_MISSING_GWT`.
- Provenance is strict: any commit after `trace` or after the reviewed handoff that touches a file outside `<docs_root>/entregas/` and outside the `provenance.ignore` entries shared by the config at the recorded head and the current one (including a trace JSON written elsewhere) makes `acceptance-report` block with `merge.stale_trace` / `merge.stale_verdict`; manual tests from an earlier delivery must be re-run and recorded for this delivery.
- Plan `**Base:**` should be a commit sha (two-dot diff, see above). Branch names or tags that move make handoff diffs wrong.
- `build-handoff` requires the plan to be committed work relative to a reachable base; it diffs against `HEAD`, so uncommitted changes are not in the handoff.
- `build-handoff --mode pr` writes inside the repository, under `.baco/logs/`; when that folder is not git-ignored, its files show as untracked (never committed by the engine).
- `build-handoff --mode repositorio` uses `git archive`, so files marked `export-ignore` in `.gitattributes` are missing from the copy, and a project file named `REVISAO.md` or `mudancas.diff` at the repository root is overwritten in the copy (never in the repository). It needs `tar` on the PATH.
- `validate-spec`, `spec-diff` and `trace` rely on documented heading/bullet/table shapes; a definition in another shape is not counted. `validate-spec` reports the common shapes (`UNRECOGNIZED_DEFINITION`, `NO_DEFINITIONS`), but an ID that does not lead its line, or a bold ID followed by prose with no separator (`**CA-001** foi revisado`), is taken as a mention and not reported (check `counts`). `spec-diff` does not report unrecognized shapes; run `validate-spec` first.
- The YAML config reader is a subset (no anchors, multiline scalars or tabs).
- `--help` and unknown-command messages are always pt-BR regardless of `language`.
- `run-tests` judges a stale queue lock by its pid only; after a reboot or with pid reuse, a lock may be judged alive when it is not (remove `/tmp/baco-queue/baco-test-queue.lock` by hand). The queue folder is open to every user on purpose, so the queue is cooperative, not a security boundary: any local user can remove a live lock or, by creating `/tmp/baco-queue` first with other permissions, block the queue (the command then stops with exit 65 naming the folder). A folder given by `BACO_QUEUE_DIR` that already exists keeps its permissions; if it is not writable by every user of the queue, a dead lock of another user stops the command (exit 65) until it is removed by hand. `.baco/local.env` can override any variable, `PATH` included, and is not checked by `guard-tests`. The JUnit check sees only top-level `*.xml` in `tests.junit_dir` (as `trace` does).
